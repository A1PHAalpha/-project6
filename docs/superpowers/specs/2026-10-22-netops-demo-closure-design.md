# NetOps Console 演示闭环设计

- 日期：2026-10-22
- 状态：已批准（2026-10-23 按推荐默认继续）
- 目标口径：先保证演示闭环，再做生产硬化

## 1. 背景与意图

项目已经具备完整的数据模型、采集、RAG 诊断、知识库、人工终端和人工变更链路，后端测试与前端构建也能通过。但上一轮审查发现，若干“页面上已经承诺”的能力在实际执行层没有闭环，演示时容易被直接看见：

- 采集计划只保存配置，没有调度执行。
- React 诊断页的报告导出不可用。
- 诊断建议的快速执行数据结构与终端 API 不匹配。
- Ping 业务失败会被统计成采集成功。
- 写命令二次确认只在前端生效。
- CI 缺少 `pysnmp`，测试任务在干净环境可能直接失败。

本设计不追求一次性把所有功能补齐，而是选择一条**可演示、可验收、可回滚**的纵向推进路线：沿“诊断、采集、终端、验证”逐条链路收口，再进入生产硬化。

## 2. 目标

1. 演示主链路连续可用：总览 → 设备/采集 → 诊断 → 证据/知识依据 → 人工终端 → 报告导出。
2. 页面上展示的能力与实际执行一致，不再出现“按钮看起来可用但没有后端行为”的情况。
3. 关键数据语义正确：不可达不能被统计为可达，失败不能被展示为成功。
4. P0 安全边界可验证：终端写命令必须经过后端确认，不能只依赖前端正则。
5. 建立回归基线：新增行为有测试覆盖，CI 在干净环境可执行。
6. 为后续生产硬化留下清晰边界，而不是把生产问题混入演示修复。

## 3. 非目标

- 不在本阶段实现生产级多用户、细粒度 RBAC、HTTPS、反向代理或多副本部署。
- 不在本阶段迁移旧版变更/评测页面到 React。
- 不在本阶段实现模型工具循环、网络搜索适配器、知识文章编辑/导入。
- 不在本阶段重做整体视觉设计或信息架构。
- 不在本阶段引入外部队列、独立数据库或微服务拆分。

## 4. 反目标

- 不为了让演示“看起来完整”而继续展示未实现的自动调度能力。
- 不让模型拥有直接下发配置的路径。
- 不通过前端遮罩掩盖后端数据错误。
- 不重写已稳定的数据库迁移和证据链，只做增量迁移。
- 不为修复单点问题引入新的重型框架或运行时依赖。

## 5. 约束

- 保持现有模块边界：`collector`、`control`、`rag_engine`、`knowledge_base`、`webapp`、`frontend`。
- 保持 `/api/v1` 契约向后兼容；旧版 `/api` 页面继续可用。
- 数据库结构变更必须新增迁移，不能改写已发布迁移。
- 时间继续使用 UTC ISO 8601；前端负责本地化展示。
- 现有 83 个后端测试、10 个前端单元测试作为回归基线。
- 单进程、单用户、SQLite + Chroma 的部署形态在本阶段不变。
- 真实设备与真实 LLM 不作为演示的前置条件；Mock 模式和合成证据必须能完整演示。

## 6. 现状证据

| 现象 | 证据位置 |
|---|---|
| 采集计划无调度消费者 | `webapp/api/v1/router.py` 的 `collection-schedule`；全局无 scheduler |
| 报告导出参数错误 | `frontend/src/features/diagnosis/AiWorkspace.tsx` 使用 `session.id` 调用 `/api/export/{diagnosis_id}` |
| 建议命令是对象数组 | `webapp/api/v1/router.py` 的 `_session_detail_dto`，`fix_suggestions` 未映射为字符串 |
| Ping 失败仍算成功 | `collector/connectivity_test.py` 只要 SSH 执行成功就返回 `status=success` |
| 写命令确认仅前端 | `control/terminal_service.py` 只对 `quick_action` 检查 `confirmed` |
| CI 缺依赖 | `.github/workflows/ci.yml` 只安装 `requirements/dev.txt`，未安装 `collect.txt` |

## 7. 方案对比

### 方案 A：按业务链路纵向修复（已选）

按“诊断链路 → 采集链路 → 终端安全 → 验证与 CI”逐条收口，每条链路完成后即可演示和验收。

- 优点：每一步都能看到结果，问题定位范围小，适合演示前推进。
- 代价：早期不会一次性清理所有技术债；部分生产问题留到第二阶段。

### 方案 B：按技术层横向修复

先统一修数据语义和 API，再修前端，最后处理 CI。

- 优点：底层更整齐。
- 代价：中途页面仍不可用，演示反馈慢。

### 方案 C：按风险等级修复

先修安全、数据正确性和 CI，再修 UI。

- 优点：生产风险最低。
- 代价：投入大、见效慢，容易在演示前把时间花在不可见改造上。

选择 A，原因是当前明确目标是先保证演示闭环，同时保留生产硬化的后续阶段。

## 8. 分阶段执行设计

### 阶段 0：基线与保护网

**目标**：在改动前固定当前可重复的验证基线。

工作项：

- 记录当前后端测试、前端测试、构建和 E2E 结果。
- 修复 CI 的依赖安装：让测试环境能够导入 `collector.collector_snmp`。
- 为本次要改的行为建立失败测试或最小复现：
  - Ping 不可达统计
  - 报告导出参数
  - 建议命令 DTO
  - 终端写命令确认
- 明确 Mock/Live 的差异，不把真实设备或真实 LLM 作为验收前提。

退出标准：

- 干净环境安装依赖后，后端测试可启动。
- 新增测试能在修复前稳定失败、修复后通过。

### 阶段 1：诊断链路闭环

**目标**：让“诊断 → 证据 → 建议 → 导出”在 React 端真正可用。

工作项：

- 报告导出：
  - 增加按会话导出能力，例如 `GET /api/v1/sessions/{session_id}/report`。
  - 后端根据会话找到最近一次诊断记录，复用现有 Markdown 导出逻辑。
  - 启用诊断页顶部导出按钮，并修正会话条中的导出链接。
- 建议 DTO：
  - `fix_suggestions` 只提取可执行字符串（如 `action`）返回给前端。
  - 增加明确的建议目标设备字段，前端不再从 `evidence[0]` 猜测。
  - 保留 `requires_manual_confirmation` 信息。
- 会话体验：
  - 新诊断完成后将会话 ID 写回 URL。
  - 重新读取会话详情，刷新证据、知识依据、结论和建议卡片。
  - 至少提供当前会话的历史切换入口；完整会话列表可以后置。
- 工具调用：
  - DTO 提供可打开的设备名，而不是让前端解析参数 JSON 字符串。

退出标准：

- 从 Mock 和真实 API 都能导出一份可读报告。
- 快速执行按钮发送的是字符串命令，目标设备正确。
- 新诊断后结构化面板刷新，刷新页面仍能恢复会话。

### 阶段 2：采集链路与状态语义

**目标**：让“采集结果”与页面展示一致。

工作项：

- 修正 Ping 语义：
  - 区分“SSH 命令执行成功”和“目标可达”。
  - `parsed.reachable=false` 时，设备可达性、连通性统计和采集摘要必须体现失败。
  - 保留原始输出和观测事实，便于诊断追溯。
- 采集计划改为真实状态：
  - 演示阶段不实现完整调度器。
  - 将“自动采集已开启”改为真实状态：未启用调度时明确显示“计划配置，尚未执行”。
  - 默认 `enabled` 改为关闭，避免首次启动就承诺自动采集。
  - 不删除配置字段；生产硬化阶段再接入调度器。
- 手动采集反馈：
  - 创建采集任务后轮询 `job_id`。
  - 展示 queued/running/success/failed 状态，并刷新采集批次列表。
- 采集批次详情：
  - 让概览页“查看”按钮真正打开对应批次详情，或至少定位到批次列表。

退出标准：

- Ping 失败时总览、设备状态和采集摘要一致显示失败。
- 页面不再声称自动采集正在运行。
- 手动采集能看到任务状态变化。

### 阶段 3：终端安全边界

**目标**：让“写命令需要二次确认”在后端成立。

工作项：

- 后端写命令检测：
  - 覆盖 Cisco/Huawei/Linux 常见写操作前缀。
  - 手工终端写命令必须携带 `confirmed=true`。
  - 快速操作继续要求确认。
- 备份状态：
  - 明确“仅确认提醒”和“已完成实际备份”的区别。
  - 至少记录确认时间；如要求实际备份，则调用现有备份接口后才允许写命令。
- 审计：
  - 记录命令来源、确认状态、会话、设备和结果。
  - 失败和拒绝也要留下事件。

退出标准：

- 直接调用终端 API 发送写命令且不确认时被拒绝。
- 合法确认后命令进入审计并可追溯。
- 既有终端测试和新增安全测试通过。

### 阶段 4：验证、CI 与文档收口

**目标**：让改动可重复验证，并让文档与实现一致。

工作项：

- CI：
  - 安装 `collect.txt` 或把设备依赖纳入开发依赖。
  - 增加本次新增测试。
  - 评估是否在 CI 运行 Playwright；至少修复桌面端拖动测试的几何条件。
- 回归：
  - 后端全量测试、ruff、compileall。
  - 前端单元测试、构建。
  - 桌面与移动端 E2E 冒烟。
- 文档：
  - 更新 API 文档中的报告导出接口。
  - 更新采集计划说明，避免“自动调度已实现”的误导。
  - 更新操作手册中的导出和终端确认流程。
- 发布检查：
  - `python start.py --check`
  - Mock 启动冒烟
  - 知识库检索冒烟

退出标准：

- 所有新增测试通过。
- CI 在干净环境通过。
- 演示脚本可以从空数据库开始完整跑通。

### 阶段 5：生产硬化（后续）

不在本次演示闭环内，但需要保留为后续清单：

- 真正的采集调度器：周期、时间窗、并发、超时、重试、范围。
- 任务持久化、取消、重启恢复。
- v1 API 的 RBAC、细粒度权限、多用户。
- 生产部署、反向代理、HTTPS、限流、CSRF 策略。
- 知识库索引备份、回滚、跨进程锁、真实增量构建。
- 模型工具循环、网络搜索适配器、流式/可取消 LLM 调用。
- 设备编辑、台账导入导出、知识文章编辑/导入、变更附件。
- SQLite WAL、缓存层或物化表。

## 9. 关键设计决策

1. **报告以会话为入口**  
   用户从诊断页导出时拿到的是会话 ID，因此 v1 层负责把会话解析为最近一次诊断，再复用旧导出器；不要求前端知道 `diagnosis_id`。

2. **建议 DTO 面向展示，不直接透传模型对象**  
   模型输出结构可能变化，API 层必须把 `fix_suggestions` 归一化为字符串命令和目标设备；前端不解析模型原始 JSON。

3. **采集状态以观测事实为准**  
   Ping 的 `status` 不能同时表示“命令执行”和“目标可达”；两者必须在数据模型或统计层分开。

4. **演示阶段不伪装调度器**  
   在完整调度器落地前，页面必须显示真实状态，默认不启用自动采集。生产硬化阶段再实现执行器。

5. **终端确认在后端裁决**  
   前端确认只负责交互；后端必须独立判断写命令和确认状态，避免 API 直调绕过。

6. **CI 与本地使用同一依赖集合**  
   设备采集依赖属于测试运行必需依赖，不能只在开发者本地 `start.py` 中安装。

## 10. 测试策略

- 单元测试：DTO 映射、Ping 统计、写命令识别、报告解析。
- 数据库测试：会话 → 诊断 → 报告关联；采集状态统计。
- API 测试：v1 导出、建议 DTO、终端拒绝/放行。
- 前端单元测试：建议命令渲染、导出链接、会话刷新。
- E2E：诊断 → 导出；手动采集 → 状态；终端写命令确认。
- 回归门禁：后端全量测试、ruff、compileall、前端测试、构建、桌面/移动冒烟。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 真实 LLM 输出不稳定 | 用固定 DTO 和 Mock 回答测试，不依赖真实模型做单元测试 |
| 真实设备不可用 | Mock/合成证据作为演示基线，真实设备作为附加验证 |
| 调度器范围膨胀 | 本阶段只做“真实状态”，调度实现后置 |
| 旧版 API 兼容性 | 新增 v1 接口，不删除旧接口；旧页面继续可用 |
| SQLite 并发写 | 保持单进程；新增任务避免并发写同一 Chroma/SQLite 资源 |
| E2E 布局敏感 | 修复测试几何条件，不把布局偶然性当作业务失败 |

## 12. Builder check 后的补充决策

### 已由设计侧决定

1. **诊断建议扩展 Prompt 契约**  
   在 `diagnosis_v2` 中为每条 `fix_suggestions` 增加：
   - `action`：人类可读的建议
   - `command`：可选的单条可执行命令
   - `target_device`：可选的目标设备名
   - `requires_manual_confirmation`
   - `kb_refs`

   旧诊断记录没有 `command`/`target_device` 时只展示文本，不提供快速执行。`check_steps` 仍然只作为检查步骤，不自动转成终端命令。

2. **历史数据不重写**  
   本次修复只保证新产生的采集结果和新读取的配置语义正确。历史 `parsed.reachable=false` 但 `collection_status=success` 的记录不回写，避免破坏已发布证据链。  
   新装或空库默认 `collection_schedule.enabled=false`；如果旧库已保存 `enabled=true`，页面显示“计划配置已保存，调度器未启用”，不伪装为运行中。

3. **报告导出以会话为入口**  
   新增 v1 会话报告接口；旧 `/api/export/{diagnosis_id}` 保留，不在本次删除。

### 已确认的人工决策

1. **验收演示运行方式**：采用两层验收。
   - Mock 模式负责 UI 演示。
   - Live 模式 + 种子采集证据 + 预置诊断记录，负责验证报告导出、建议 DTO、终端拒绝等后端真实链路。
   - 不依赖真实 LLM 和真实设备。

2. **写命令的备份门槛**：必须完成实际备份。
   - 终端界面增加“执行备份”动作。
   - 写命令在 `backup_status=completed` 前一律拒绝。
   - 无设备时保留并演示拒绝路径。

3. **确认机制**：使用服务端签发的一次性确认令牌。
   - 绑定会话、命令哈希和短有效期。
   - 不接受仅靠请求体 `confirmed=true` 的写命令。
   - 令牌一次性使用，失败或过期后必须重新确认。

## 13. 留给实施者的决定

- 报告接口的具体路径和响应头。
- 写命令前缀清单的维护位置和扩展方式。
- 会话历史入口的具体交互形式。
- 手动采集轮询的间隔、超时和失败提示文案。
- 是否在本阶段引入最小调度器测试替身，还是只测试“计划状态真实展示”。

以上决定不改变本设计的业务边界，实施者可以在计划阶段给出具体方案。
